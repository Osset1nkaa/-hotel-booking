# Hotel Booking — Design Notes

# P03 — первая версия приложения

## 1. Зачем проектировать до написания кода?

Проектирование помогает согласовать правила бронирования,
распределить обязанности и заранее определить возможные ошибки.

Главная проблема — пересекающиеся бронирования одного номера.
Сначала нужно понять правило, затем реализовать его в коде.

## 2. Требования

В P03 определены пять требований:

- R1 — поиск свободных номеров.
- R2 — создание бронирования с уникальным ID.
- R3 — отклонение пересекающихся бронирований.
- R4 — отмена бронирования и освобождение номера.
- R5 — просмотр бронирования по ID.

Главное правило:
один номер в одну ночь может иметь не более одной
подтверждённой брони.

Дата выезда не входит в период проживания.
Поэтому заезд в день выезда другого гостя разрешён.

Обычные последовательные запросы проверяются по этому правилу.
Защита от конкурентного бронирования требует отдельного решения.

## 3. Варианты использования

Пользователи приложения:

- Guest — гость.
- Receptionist — администратор отеля.

Оба пользователя могут искать свободные номера,
создавать, отменять и просматривать бронирования.

Все запросы должны использовать общее хранилище бронирований.

## 4. Классы и обязанности в P03

Room хранит ID и тип номера.

Reservation хранит:

- ID бронирования;
- имя гостя;
- ID номера;
- дату заезда;
- дату выезда;
- статус.

В исходной версии P03 использовались отдельные функции:

- isRoomFree — проверка пересечения подтверждённых броней.
- searchFreeRooms — поиск свободных номеров.
- bookRoom — проверка данных и создание бронирования.
- viewBooking — поиск бронирования по ID.
- cancelBooking — изменение статуса на Cancelled.
- validateDates — проверка дат.

Массивы rooms и reservations хранили данные в памяти.
После завершения программы данные не сохранялись.

## 5. Последовательность бронирования

1. Получить имя гостя, ID номера и даты.
2. Проверить, что имя не пустое.
3. Проверить формат и существование календарных дат.
4. Проверить, что выезд позже заезда.
5. Проверить существование номера.
6. Проверить пересечение с подтверждёнными бронированиями.
7. При пересечении вернуть Unavailable.
8. Если проверки пройдены, создать уникальный ID.
9. Сохранить бронирование со статусом Confirmed.
10. Вернуть Accepted и ID бронирования.

Некорректные данные отклоняются до создания бронирования.
Поиск с неправильными датами выдаёт ошибку.

Два периода пересекаются, если:

newCheckIn < existingCheckOut
и
newCheckOut > existingCheckIn.

Отменённые бронирования не блокируют номер.

## 6. Последовательность отмены

1. Получить ID бронирования.
2. Найти бронирование.
3. Если оно отсутствует, вернуть Booking not found.
4. Если уже отменено, вернуть Already cancelled.
5. Иначе изменить статус на Cancelled.
6. Вернуть подтверждение отмены.

Бронирование остаётся доступным для просмотра.
Проверка доступности больше не учитывает его как занятой период.

## 7. Решения в процессе бронирования

Основные вопросы:

- Корректны ли данные?
- Существует ли номер?
- Свободен ли номер на указанные даты?

Бронирование создаётся только после успешного прохождения
всех проверок.

## 8. Реализация и наблюдаемые результаты

Язык: JavaScript.
Среда выполнения: Node.js v22.14.0.

В демонстрации:

- Maya получает бронь R101 на R7 с 12 по 14 ноября 2026 года.
- Запрос Omar на R7 с 13 по 15 ноября отклоняется.
- Запрос Omar на R8 с 13 по 15 ноября принимается как R102.
- Просмотр R101 показывает данные Maya.
- Отмена R101 меняет статус на Cancelled.
- После отмены R7 снова доступен на эти даты.
- Поиск с 13 по 15 ноября возвращает только R7.
- Поиск с 16 по 18 ноября возвращает R7 и R8.

Проверки также отклоняют пустое имя,
несуществующую дату и выезд раньше заезда.

## 9. Эксперимент с гонкой

Эксперимент выполнен во время P04.

Команда:

node race-demo.js

В отдельной демонстрационной функции создана искусственная
пауза между проверкой доступности и сохранением брони.

Maya и Omar проверяют один номер R7 на одинаковые даты.
Оба запроса видят номер свободным.
После паузы оба сохраняют подтверждённые бронирования.

Наблюдаемый результат:

Double booking!

Причина: проверка и сохранение выполняются как отдельные
действия, между которыми другой запрос может изменить данные.

Это демонстрация небезопасной последовательности
«проверить, затем сохранить».

Она не доказывает наличие гонки в обычном синхронном
методе bookRoom: внутри него между проверкой
и сохранением нет await.

Рефакторинг P04 сам по себе не решает проблему
конкурентного бронирования.


# P04 — улучшение структуры приложения

## 1. Исходное состояние перед P04

Этот раздел описывает приложение до рефакторинга.

Версия P03 использовала отдельные функции и общие массивы
в hotel_booking.js.

В одном файле находились:

- классы предметной области;
- правила бронирования;
- проверка данных;
- хранение в памяти;
- демонстрационный вывод.

BookingService, заменяемые хранилища и отправители уведомлений
на этом этапе ещё не были реализованы.

## 2. Цель рефакторинга

Рефакторинг — изменение внутренней структуры программы
с сохранением её существующего поведения.

Цель P04:

- отделить правила бронирования от хранения;
- выделить классы предметной области;
- передавать зависимости через конструктор;
- обеспечить возможность замены отправителя уведомлений;
- проверить сохранение поведения тестами.

Уведомления отсутствовали в нашей исходной версии P03.
Их добавление является отдельной новой возможностью.

## 3. Проверка поведения до рефакторинга

Команда:

node --test

Результат:

6 тестов пройдено, 0 ошибок.

Проверялись:

1. Поиск свободных номеров.
2. Создание и просмотр бронирования.
3. Отклонение пересекающейся брони.
4. Заезд в день выезда другого гостя.
5. Отмена брони и освобождение номера.
6. Отклонение некорректных данных.

Эти тесты зафиксировали поведение, которое нужно сохранить.

## 4. Анализ исходной структуры по SOLID

### S — Single Responsibility Principle

Исходный файл объединял несколько обязанностей:
хранение, правила бронирования, проверку данных и вывод.

Изменение одной части усложняло работу с остальными.
Обязанности следовало разделить.

### O — Open/Closed Principle

Для замены массива другим хранилищем потребовалось бы
изменять функции бронирования.

Контракт хранилища позволяет подключать другую реализацию
без изменения правил бронирования, если она соблюдает
тот же способ взаимодействия.

### L — Liskov Substitution Principle

В исходной версии не было взаимозаменяемых реализаций,
поэтому нарушение этого принципа не было установлено.

После выделения контрактов реализации должны соблюдать
одинаковое ожидаемое поведение.

### I — Interface Segregation Principle

Хранилищу и отправителю нужны разные методы.
Их контракты следует разделять.

Отправитель уведомлений не должен реализовывать
методы поиска и хранения бронирований.

### D — Dependency Inversion Principle

Исходные функции напрямую обращались к глобальным массивам.

BookingService должен получать зависимости извне
и использовать согласованные методы хранилища и отправителя.

## 5. Структура после рефакторинга

main.js:
создаёт объекты, выбирает отправитель и запускает демонстрацию.

src/domain.js:
содержит классы Room и Reservation.

src/stores.js:
содержит ReservationStore — хранилище бронирований в памяти.

src/notifications.js:
содержит EmailSender и SmsSender.

src/booking.js:
содержит BookingService с правилами бронирования.

test/booking.test.cjs:
содержит восемь автоматических тестов.

race-demo.js:
содержит отдельную демонстрацию небезопасного
конкурентного бронирования.

package.json:
описывает проект и команды запуска.

Исходный код P03 сохранён в docs/hotel_booking.js.
Точка входа версии P04 — main.js.

## 6. Контракты и передача зависимостей

BookingService получает через конструктор:

- rooms — список номеров;
- store — хранилище бронирований;
- sender — отправитель уведомлений.

Контракт ReservationStoreContract:

- all();
- add(reservation);
- findById(id).

Контракт NotificationSender:

- send(reservation).

В JavaScript нет отдельного ключевого слова interface.
В этом проекте контракт определяется ожидаемым набором
методов и их поведением.

На диаграмме контракты обозначены как «interface».

Текущие методы хранилища и отправителя синхронные.
Асинхронная реализация потребует согласования контракта
и соответствующих изменений обработки вызовов.

## 7. Принципы SOLID после изменений

### S — единственная ответственность

BookingService отвечает за правила бронирования.
ReservationStore отвечает за хранение.
EmailSender и SmsSender отвечают за уведомления.
main.js соединяет объекты и запускает пример.

### O — открытость для расширения

Добавлен SmsSender без изменения BookingService.
Выбор отправителя выполняется в main.js.

### L — подстановка

EmailSender и SmsSender поддерживают метод send(reservation).
BookingService может работать с любым из этих отправителей.

Одинакового названия метода недостаточно:
реализации должны соблюдать согласованное поведение.

### I — разделение интерфейсов

Контракт хранения отделён от контракта уведомлений.
Каждая зависимость предоставляет только необходимые методы.

### D — инверсия зависимостей

BookingService получает хранилище и отправитель
через конструктор.

Он не создаёт внутри себя конкретные ReservationStore,
EmailSender или SmsSender.

## 8. Новое требование R6

Бронь сохраняется до отправки подтверждения.

Подтверждение отправляется только для принятой брони.
Отклонённый запрос не вызывает отправку.

Если отправитель выдаёт ошибку, сохранённая бронь
остаётся Confirmed и продолжает занимать номер.

Ошибка уведомления не отменяет успешно созданную бронь.
Результат бронирования остаётся Accepted.

## 9. Поддельный отправитель и проверка ошибки

В тесте 7 используется поддельный отправитель.

Он записывает вызовы и позволяет проверить:

- подтверждение отправляется для принятой брони;
- бронь уже сохранена в момент отправки;
- отклонённая бронь не вызывает отправку.

В тесте 8 отправитель специально выдаёт ошибку.

Проверяется, что:

- результат бронирования остаётся Accepted;
- бронь доступна по ID;
- статус остаётся Confirmed;
- номер остаётся занят;
- пересекающийся запрос отклоняется.
