# Hotel Booking — Requirements

## Среда и общие правила

Язык: JavaScript.
Среда выполнения: Node.js.

Номера и бронирования хранятся в памяти.
Будущие запросы с сайта и от администратора должны
использовать одно общее хранилище.

Дата заезда включается в проживание.
Дата выезда не включается: [checkIn, checkOut).

## R1 — Поиск свободных номеров

Система должна возвращать номера, свободные
на весь запрошенный период.

Только бронирования со статусом Confirmed блокируют номер.

Пример:
R8 занят с 13 по 15 ноября 2026 года.
После отмены брони Maya на R7 поиск на эти даты
возвращает только R7.

Доказательство:
Тест 1 проверяет поиск до и после бронирования.
Демонстрация main.js показывает поиск после отмены.

## R2 — Создание бронирования

Система должна создавать бронирование со статусом
Confirmed для существующего свободного номера.

Каждое бронирование получает уникальный ID
в пределах общего хранилища текущего запуска.

Пример:
В демонстрации Maya получает R101.
Затем Omar бронирует R8 и получает R102.

Доказательство:
Тест 2 проверяет создание брони R101,
её данные и доступность по ID.
Демонстрация показывает создание R101 и R102.

## R3 — Запрет пересекающихся подтверждённых броней

Система должна отклонять запрос, если подтверждённая
бронь уже занимает тот же номер хотя бы на одну
из запрошенных ночей.

Два периода пересекаются, если:

newCheckIn < existingCheckOut
AND
newCheckOut > existingCheckIn.

Заезд в день выезда другого гостя разрешён.

Пример:
Maya занимает R7 с 12 по 14 ноября.
Запрос Omar на R7 с 13 по 15 ноября отклоняется.
Заезд другого гостя 14 ноября разрешён.

Доказательство:
Тест 3 проверяет отказ при пересечении.
Тест 4 проверяет заезд в день выезда.

Ограничение:
Тесты подтверждают правило для последовательных вызовов.
Защита от конкурентного бронирования не реализована.

Отдельная демонстрация node race-demo.js показывает,
как искусственная пауза между проверкой и сохранением
позволяет создать две пересекающиеся брони.

Она демонстрирует небезопасную последовательность действий,
а не гонку внутри обычного синхронного bookRoom.

Критерий для будущего решения:
два конкурирующих запроса на один номер
с пересекающимися датами не должны оба приниматься.

## R4 — Отмена бронирования

Система должна изменять статус существующей брони
на Cancelled.

Отменённая бронь остаётся доступной для просмотра,
но больше не блокирует номер.

Номер становится доступным, если на эти даты
нет другой подтверждённой брони.

Пример:
Maya отменяет R101.
Omar может забронировать освободившийся R7.

Доказательство:
Тест 5 проверяет статус Cancelled
и успешное бронирование освободившегося номера.

## R5 — Просмотр бронирования

Система должна находить бронирование по ID
и возвращать:

- ID бронирования;
- имя гостя;
- ID номера;
- дату заезда;
- дату выезда;
- статус.

Для неизвестного ID возвращается null.

Пример:
Просмотр R101 показывает данные Maya
и текущий статус её брони.

Доказательство:
Тест 2 проверяет данные сохранённой брони
и результат null для неизвестного ID.
Тест 5 проверяет просмотр статуса после отмены.

## R6 — Ошибка уведомления не теряет бронирование

Система должна сохранять подтверждённую бронь
до попытки отправки уведомления.

Уведомление отправляется только для принятой брони.
Отклонённый запрос не вызывает отправку.

Если отправитель выдаёт ошибку:

- бронь остаётся сохранённой;
- статус остаётся Confirmed;
- результат бронирования остаётся Accepted;
- номер остаётся занят на даты проживания.

Пример:
Бронь Maya сохранена, но отправитель выдаёт ошибку.
Бронь доступна по ID.
Пересекающийся запрос Omar отклоняется.

Доказательство:
Тест 7 проверяет отправку после сохранения
и отсутствие отправки для отклонённого запроса.
Тест 8 проверяет сохранность брони при ошибке отправителя.

## Проверка входных данных

Имя гостя должно быть строкой и не должно быть пустым
или состоять только из пробелов.

Даты должны существовать в календаре
и иметь формат YYYY-MM-DD.

Дата выезда должна быть позже даты заезда.
Указанный номер должен существовать.

Некорректный запрос не создаёт бронирование.
Поиск с неправильными датами выдаёт ошибку.

Доказательство:
Тест 6 проверяет:

- пустое имя;
- несуществующую дату 2026-02-30;
- выезд раньше заезда;
- несуществующий номер R99;
- ошибку поиска при неправильных датах;
- отсутствие созданной брони после отказов.

## Границы версии P04

Реализовано консольное приложение.

Данные хранятся в памяти и теряются
после завершения программы.

EmailSender и SmsSender выводят демонстрационные
сообщения в консоль.
Реальные email и SMS не отправляются.

Не реализованы:

- база данных;
- HTTP API и интерфейс сайта;
- платежи;
- авторизация пользователей;
- защита от конкурентного бронирования.
